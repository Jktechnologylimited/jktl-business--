# JKTL Games security audit and hardening

Date: 28 October 2026, Africa/Lagos.

## Executive summary

The reviewed game surfaces have useful existing controls, but confirmed weaknesses in credential revocation, Business recovery, membership enforcement, abuse controls and team-page authorization required changes. Those findings are fixed in source and tested locally. No critical vulnerability was confirmed in the reviewed scope. This is not a certification that the platform is completely secure or production-ready.

The immediate rollout priority is deploying Fantasy and Business with the compatible dependency lockfile updates, communicating the session/password behavior below, then checking the actual hosting, database and secret settings. No production database, email, payment, DNS or credential was modified during this audit.

## Scope actually inspected

- `scaling-waffle-gam-fant-jktl`: all three API route files (Auth.js, daily cron, health), all four Server Action modules (34 exported actions), authentication, password/token/session code, SQL access, market-data ingestion, portfolios, valuations, rankings, achievements, leagues, profiles, team pages, browser storage, email integration, migration/seed/reset scripts, package/lockfile, security headers and Vercel configuration.
- `jktl-business--`: Tycoon API, game document parsing and client save flow, account session/recovery/login code shared with Tycoon, Growth & Gaming identity linkage/permissions, game return destinations, game-host routing, framing policy and integration dependencies. The full existing Business test suite was run; this is **not** a claim that every unrelated Business billing, website-builder or support action received a new manual security audit.
- No puzzle implementation, daily puzzle-answer endpoint, Games content-management upload system, separate gaming team-invitation flow or other Games repository is present in the mounted source. Those features were not invented or represented as reviewed.
- Main's existing game embedding was preserved. Main itself was not re-audited as part of this Games brief.

## Findings and remediation

| ID | Severity | Component / evidence and root cause | Impact | Remediation | Status |
| --- | --- | --- | --- | --- | --- |
| G-01 | High | Fantasy `auth/config.ts`, `auth/session.ts`: authorization used rolling JWT `iat`, rounded to seconds; missing timestamps were accepted. Auth.js can re-encode the JWT with a fresh `iat`. | A copied, old token could outlive password-reset revocation through refresh; same-second changes were ambiguous. | Capture the verified account's millisecond credential version at login, preserve it across JWT updates and compare it to the live account on every protected request. Legacy/malformed tokens fail closed. | Fixed; callback, same-second reset and refreshed-token regressions pass. |
| G-02 | Medium | Fantasy `services/users.ts`: token consumption, password replacement and audit were separate transactions; concurrent token issuances did not lock the account. | A failed update could consume a valid recovery link without changing the password, and concurrent issuance could retain multiple links. | Serialize issuance on the user row; lock/recheck and consume reset tokens, change credentials, invalidate siblings and append the audit entry in one transaction. Ensure the version advances by at least one millisecond. | Fixed; concurrent reuse succeeds once; forced update failure rolls back token consumption. |
| G-03 | High | Business `db/auth.ts`: recovery selected an unused token, then changed the password and marked tokens separately; password changes did not delete account sessions. | Concurrent token reuse and continued use of stolen sessions after recovery. | Lock and consume the token, replace the password, invalidate other recovery links and revoke all Business sessions atomically. Password changes use the verified old hash in the update condition and revoke sessions/reset links in the same statement. | Fixed; real local PostgreSQL concurrent replay, rollback and other-user preservation checks pass. |
| G-04 | High | Business `validateSession` trusted an unexpired session without checking current membership; `verifyLogin` selected inactive memberships too. | A removed/inactivated member could retain tenant/account access, including game saves. | Require an active membership for both login and every session validation; reject malformed session IDs before querying. Tenant identity remains server-derived. | Fixed; inactive membership and SQL-injection-shaped ID tests pass. |
| G-05 | Medium | Business `auth-actions.ts`: recovery URLs were built from request `Host`. | Reset links could use an unintended host on this multi-host deployment. | Use only configured `NEXT_PUBLIC_APP_URL` (default `https://business.jktl.com.ng`), validate protocol and reject credentials in the configured URL. Request headers no longer control recovery links. | Fixed; hostile-Host regression passes. |
| G-06 | Medium | Business account login, signup and recovery had no shared throttles at these entry points. | Password guessing, recovery-mail spam and excessive account creation. | Shared atomic database buckets for IP/account login, signup, reset request/submission and password changes. Account/IP subjects are hashed before storage. | Fixed; concurrent shared-bucket limit test passes. Trusted proxy-header handling remains a hosting verification item. |
| G-07 | Medium | Tycoon `PUT /api/tycoon` allocated the entire body before checking its character length; account save requests had no shared rate limit. | Excessive memory/database consumption; multibyte bodies exceeded the intended byte budget. | Enforce JSON and a 12,000-byte limit while streaming; cancel oversized reads, reject null/scalar/malformed data, limit writes to 30/minute and account reads to 120/minute. Actual limit violations return 429/Retry-After; backend outages remain 503. Compare full same-origin scheme/host before mutations. | Fixed; bounded-stream, UTF-8, hostile-origin, throttling and account-isolation tests pass. |
| G-08 | Medium | Twelve Fantasy team pages relied on the parent layout instead of checking access before reading their data; only Users checked locally. | A cached layout was an inadequate boundary for subsequent page/RSC data access after role/session changes. | Every one of the 13 team pages checks `requireAdminPage` independently before loading data. Existing team actions retain their separate `assertAdmin` checks. | Fixed; all pages and all exported team actions are covered by authorization tests. |
| G-09 | Medium | Business new passwords allowed six characters and silently inherited bcrypt's 72-byte truncation. | Weak new credentials and ambiguous overlong passwords. | New signup/reset/change credentials require at least ten characters and at most 72 UTF-8 bytes; UI guidance matches. Existing login/current-password inputs remain compatible with legacy passwords, with an input-size bound. | Fixed for the reviewed normal-account paths. Separate affiliate/team password policy is outside this integration change. |
| G-10 | Medium | Business account/team pages lacked an explicit anti-framing policy. | Account UI could be framed for clickjacking. | Deny framing on account, Business dashboard, team, affiliate and partner surfaces. Preserve the explicit public Tycoon embedding allowlist; add nosniff/referrer headers and suppress the framework branding header. | Fixed; built-app header checks pass. No blanket restriction was applied to customer website embedding. |
| G-11 | Low | Fantasy public health exposed missing configuration names; unexpected action/cron errors logged raw error messages. | Unnecessary deployment details and potentially sensitive error content in logs. | Public readiness returns only status; reviewed unexpected-error logs record error type instead of raw messages. | Fixed in the listed paths. This is not a claim that every historical log was scanned. |
| G-12 | Medium | Suspension blocked Fantasy access only while status remained suspended. | Restoring an account could restore a previously copied token. | Advance the credential version on suspension so the previous session stays revoked after restoration. | Fixed; suspension/restoration regression passes. |
| D-01 | High advisory severity | Business lockfile: six high-severity package entries through `source-map-js`, `undici` and vulnerable Zod versions, including the Blob/OIDC/CLI-config dependency chain. | Published dependency DoS/TLS risks; exact exploitability depends on which library paths receive attacker-controlled data. Not all six package entries are independent vulnerabilities. | Compatible patches: `source-map-js` 1.2.2, `undici` 6.29.1, Zod 4.6.7; scoped `@vercel/cli-config` override removes its vulnerable pinned Zod without downgrading Blob. | Patched; official npm audit reports zero advisories for the resulting Business tree and for Fantasy. No framework major upgrade. |

## Remediation summary and changed files

- Fantasy production changes: `src/server/auth/{config,session}.ts`, `src/server/services/{users,admin}.ts`, `src/server/actions-util.ts`, health/cron route handlers and the twelve previously unguarded team page files. No game UI redesign or database migration.
- Business production changes: `src/lib/db/auth.ts`, `src/lib/actions/auth-actions.ts`, new `src/lib/security/{auth-rate-limit,game-request}.ts`, Tycoon route handler, normal signup/reset/password-settings guidance and post-change navigation, `next.config.ts`, `package.json` and `package-lock.json`.
- Regression coverage: Fantasy auth integration tests, all-team-action tests, new `tests/unit/{auth-callbacks,team-pages}.test.ts` and session test helpers; Business new `tests/game-security.test.mjs`, existing Tycoon tests and Growth test dependency bindings. The audit report is included in both repositories.
- No extra runtime secret or schema setting is introduced. Production account-origin, mail/verification and hosting settings still require operator verification, as detailed below.

## Existing controls verified and preserved

- Fantasy uses Auth.js encrypted JWT cookies, bounded server-side validation, scrypt password hashes, hashed random single-use recovery tokens and database-backed rate counters. Role/status are read from the database, not granted by client fields. Signup cannot create a team role.
- Each team mutation checks the current team identity on the server; user role changes, market imports, source/instrument changes and round finalization are audited. Normal players cannot promote themselves. The CLI promotion/seed tools require database/operator access and are not public APIs.
- Fantasy trade price, budget, time window, eligibility and valuation come from server data. Row locks and unique idempotency keys prevent double spending/rewards on duplicate submissions. Achievements are derived from stored activity and use unique awards. The real PostgreSQL suite exercises concurrent identical orders and separate-user trades.
- Private portfolios use the authenticated user ID; leagues require membership, and invite viewing/rotation/removal require ownership. Invite codes are random and join attempts are throttled. Public profiles exclude email/passwords and disclose private league memberships only to shared members.
- SQL values are parameterized; dynamic SQL uses fixed internal fragments/allowlists. Injection-shaped symbols/IDs and hostile redirect inputs do not grant access. This review did not find an exploitable SQL injection or arbitrary server-side URL fetch in the game entry points.
- Fantasy's only game-related file ingestion is team-only CSV market data, bounded by bytes/rows with schema, timestamp and price checks. No arbitrary executable file-upload endpoint was found. Future puzzle solutions are not exposed because no such feature is present here.
- Fantasy guest trades stay in browser-local practice storage and are not imported as authoritative ranked balances. Tycoon account saves are private sandbox documents, bounded/parsed and revision-checked by user ID. **Tycoon state is still client-authored, not a verified competitive score**: do not use it for leaderboard prizes, commissions, account entitlements or money. No such reward connection was found.
- Tycoon reuses a Business session because its iframe stays on the Business origin, without widening the cookie Domain to all customer subdomains. Fantasy has its own account/session system: a Business account or Growth & Gaming role does not automatically authenticate or grant team access to Fantasy. Public email branding is a fixed trusted fetch and does not exchange account tokens.
- Fantasy's CSP limits default sources, disables plugins, restricts forms and denies protected-page framing. Only the public root game is explicitly embeddable on trusted JKTL origins. No cross-origin wildcard credentials policy or user-controlled postMessage authentication bridge was found.

## Secrets and deployment review

The tracked-source scan checked private-key headers, common provider-token formats and public secret-variable names without printing candidate values. Only `.env.example` is tracked in each audited repository; no high-confidence live secret was detected by those checks. Database/auth/provider configuration remains server-side in the inspected game paths. This was not an exhaustive historical secret scan or validation against provider inventories. No secret was rotated, and no claim is made about old commits, logs or external deployment settings.

The available repository configuration uses Next.js 16.4.2 in both applications; Fantasy React is 19.3.0 and Business React is 19.2.8. Lockfile integrity fields remain in place. No GitHub Actions workflow is present in the inspected Games repository. Public production source maps were not explicitly enabled. The daily Games cron requires a timing-safe bearer-secret check and rejects absent/wrong credentials.

Production Vercel/DNS settings, WAF configuration, actual database roles/grants, backup retention, deployed tables and secure environment bindings were **not accessible or changed**. The audit used a disposable PostgreSQL instance bound to `127.0.0.1`, with synthetic records only. Business's normal build had no DATABASE_URL and correctly skipped its prebuild schema step.

## Outstanding risks and operator actions

1. **Medium — copied Fantasy JWT after ordinary logout.** Logout clears the browser cookie; it does not maintain a server-side per-device revocation list. A separately stolen JWT can remain valid until expiry unless password reset/suspension advances its credential version. Password reset and suspension now revoke access reliably; truly immediate per-device logout revocation requires a dedicated server-side session/JTI store and coordinated migration. No silent authentication-store replacement was made.
2. **Medium — browser-game trust boundary.** Tycoon and guest practice state can be edited by their owner. Keep them disconnected from competitive/financial rewards. If competitive Tycoon is introduced, replay validated commands on the server, add per-run nonces/sequence numbers and calculate scores there; do not trust saved cash, XP or client clocks.
3. **Medium — team account assurance.** Fantasy currently has player/admin roles, not a granular team invitation/MFA system. Business's fine-grained Growth permissions are a separate boundary. Verify trusted team identities and require MFA at deployment/GitHub/database providers; consider application-level team MFA separately. No role was granted during testing.
4. **Medium — production configuration unverified.** Verify unique strong `AUTH_SECRET`/`CRON_SECRET`, production/preview DB separation, HTTPS/Secure/HttpOnly/SameSite cookies at actual hostnames, strict origin settings, Vercel's normalization of trusted client-IP headers, rate-counter cleanup and edge WAF limits. Do not share secret bindings with untrusted preview branches or customer sites.
5. **Medium — database privileges/recovery unverified.** Use an application role limited to required DML and a separate migration/operator role. Revoke schema creation/extension/role-management permissions from the app role where practical. Restrict DB access, enable provider backups/PITR, and rehearse restores on a separate branch/database; reconcile ledger cash and balances after restoration. Existing migration scripts use transactions/advisory locks; no schema change is required by this patch.
6. **Low/defense in depth — CSP and scale.** Fantasy still permits inline bootstrap scripts/styles for compatibility; a nonce-based script policy needs a separately tested rollout. Public game rendering can load rankings and market snapshots; monitor query cost and add bounded/cached public snapshots as player counts grow. Application counters do not replace platform request/body/time limits or volumetric DDoS protection.
7. **Scope gap — unavailable games.** Supply/mount any separate puzzles/Games repository before claiming its answer secrecy, score submissions, upload flows or management APIs have been audited. This report does not cover unseen code.
8. **Operational checks.** Verify mail delivery/verification policy (`EMAIL_VERIFICATION_REQUIRED` is configurable, not universally enforced), alerting for denied team actions and sustained authentication abuse, and log-retention/access restrictions. No payment/webhook/notification provider was exercised against production.

No specific live credential was identified as exposed by this audit. If provider or historical scanning finds an exposure, rotate the named secret through that provider, revoke affected sessions/tokens and remove the leak; do not paste secret values into tickets or chat.

## Rollout and compatibility

- Deploy Fantasy and Business independently; no new environment secret or database migration is required. Preserve existing remotes, customer routing and application data.
- **Fantasy:** existing JWTs without a credential version will be rejected and users must sign in again once. After suspension/restoration, sign in again. This intentional revocation behavior must be communicated to the team.
- **Business:** password reset/change signs out **all** sessions for that account, including Tycoon. The settings password form sends the user back to login after success. Inactive memberships no longer authenticate. Existing legacy passwords remain usable at login; only newly set credentials use the ten-character/72-byte rule.
- Confirm `NEXT_PUBLIC_APP_URL=https://business.jktl.com.ng` in production. Recovery links no longer follow arbitrary request/tenant hosts. Preview recovery links must point to the intended isolated account environment.
- Commit the package and lockfile together; install with `npm ci`. Keep the scoped Zod override until the upstream CLI-config pin is patched and a later audit verifies removal is safe.
- Check actual HTTPS headers/cookies after deployment, including public game embedding on Main, and monitor login/save errors. Do not relax origin or account guards to hide configuration failures.

- Browser checks against the built Fantasy app use a synthetic local account: real credentials login works; anonymous/player team access is refused; a tampered JWT is rejected; a locally revoked credential version remains rejected after a real Auth.js session refresh; cron without a bearer token and credential POST without a CSRF token are rejected; HttpOnly/SameSite and framing headers are verified. - Business built-app checks cover guest Tycoon rendering, unauthorized and cross-origin save rejection, account anti-framing headers and preserved Main embedding.

- Focused ESLint checks of the reviewed/changed server authentication, team, API and request-security code pass in both repositories. Framework TypeScript checks pass in both production builds.
- No production load testing, purchases, real emails, external account access or credential rotation. Temporary local test infrastructure is stopped after verification.
