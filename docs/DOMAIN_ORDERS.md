# Pay-per-order domains

Business owns the catalogue, customer orders, Paystack verification, domain records, audit and manual fulfillment queue. Main links to the live Business marketplace and reads its retail-only public `/api/public/domain-prices` catalogue with a short cache; it never receives supplier costs or a Business database connection. There is **no JKTL customer wallet, supplier auto-purchase, recurring domain debit or WHOIS harvesting**. The private GO54 reseller-balance snapshot is an operator record of the underlying supplier account, not customer funds. See [current GO54 contract and implementation status](GO54_INTEGRATION_STATUS.md) for authentication, pricing transport, markup controls, migration 057 and the remaining registrar API blockers.

## Deployment setup

1. Run `npm run db:migrate` against the Business database (additive migration `034_domain_orders.sql`; the deployment prebuild also includes the current additive migration list, now including 057). Take the normal database backup first. The six seeded extensions are disabled and have no retail prices; admin must configure actual supplier costs, retail registration/renewal prices, allowed years, eligibility requirements and enable each extension. All amounts are integer NGN kobo. No sample production fee is invented. Supplier names/costs are admin-only.
2. Existing `DATABASE_URL`, `PAYSTACK_SECRET_KEY`, `NEXT_PUBLIC_APP_URL=https://business.jktl.com.ng` and transactional email (`RESEND_API_KEY`, verified `RESEND_FROM_EMAIL`) must be configured in the deployment. Do not paste them into chat. Subscribe the existing signed Paystack webhook `/api/webhooks/paystack` to `charge.success` and `refund.processed` alongside existing website events. Test with Paystack test mode first.
3. Add `DOMAIN_CONTACT_ENCRYPTION_KEY`: exactly 32 random bytes, base64 encoded (`node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"` in a secure terminal). Store in the secret manager and back it up separately. AES-256-GCM authenticates registrant contact data. Missing key fails checkout before initialization. **Do not replace the key without first re-encrypting existing contacts with a controlled migration.** Losing it loses access to registrant information. Never put it in a public/browser variable.
4. Configure `CRON_SECRET`; Vercel runs the existing daily job at 07:00 UTC and `/api/cron/domains` at 08:00 UTC (09:00 in Nigeria). The second job queues domain reminders and Custom invoices/notices. Calls require the constant-time checked bearer secret. Notices use leases and provider idempotency keys. Failed sends retry after five minutes on the next invocation; monitor non-200 responses. Only one batch of 15 domain and 10 Custom notices runs per invocation; increase safely or invoke from a secure scheduler if volume exceeds daily throughput.
5. Optional `DOMAIN_AVAILABILITY_URL` (HTTPS) + `DOMAIN_AVAILABILITY_API_KEY`: server GET with `?domain=example.com.ng` and bearer authentication. Return `{domain,available:boolean,premium:false,reserved:false,eligible:true,registrationPriceKobo:integer,currency:"NGN"}`. Exact domain match is required; premium, unpriced/ineligible or lookup failures return UNKNOWN, never an invented availability result. If returned, supplier price must be positive integer kobo and no higher than retail. This is only an availability adapter, **not** a registrar purchase API. Without it the customer requests a check and admin confirms manually after supplier verification. Results expire (provider 10 minutes, manual 30) and are bound to price revision. DNS resolution/NXDOMAIN is never used as proof a domain can be registered.
6. Website connection: set `DOMAIN_WEBSITE_CNAME` to the real supported hosting CNAME and/or `DOMAIN_WEBSITE_IPV4` to supported comma-separated A targets. Do not guess a Vercel address. Existing custom-domain entitlement still applies, independently of purchasing a domain. An operator must add/check the domain and SSL on the actual hosting project, then record its reference on the CONNECT task. TXT ownership + expected DNS + hosting confirmation are all required before marking connected. No automatic Vercel API provisioning is claimed.

## Customer flow

`/domains` is the public catalogue; `/business/domains` is My Domains. Only an active organization owner may search/order/manage. Registration has no website-plan prerequisite. Domain labels, registrant contact, selected years, server price revision and explicit versioned `/domain-terms` consent are validated before reserving an order. Price/currency/total cannot be supplied by the browser. Duplicate active orders for the same domain and duplicate active renewals are blocked in PostgreSQL.

Paystack initialization is one-off, with no plan or reusable card authorization. A reserved reference is claimed once. An uncertain initialization stays pending status verification/support; it is never silently charged again. A callback is not proof of payment. Successful charges are verified server-to-server for reference, exact amount, currency, metadata, customer email and provider transaction uniqueness. Domain webhooks commit their own ledger before acknowledging; transient failure returns 503 for retry and cannot activate a website/AI subscription or fall through legacy billing.

## Operator runbook

- `/admin/domains`, owner role only: review availability checks, configure prices, inspect paid orders, handle DNS/support tasks, review audit. Unpaid registrant contact is not displayed. Paid contact is decrypted server-side for the registration task, never returned to customer catalogue APIs.
- PAID → PROCESSING: manually purchase/renew using the paid order's agreed details in the supplier dashboard. Check the supplier's current price and eligibility first. No supplier purchase happens from JKTL code.
- PROCESSING → ACTIVE requires supplier reference, confirmed actual registration/expiry dates and actual nameservers. Dates must match the purchased duration. Only this confirmation creates/extends the asset. A paid charge alone does not activate a domain. Stale admin edits are rejected by revision.
- Failure: record a customer-visible explanation and move FAILED → REFUND_PENDING. Initiate the refund through Paystack's dashboard; JKTL never accepts an arbitrary “mark refunded” toggle. Signed `refund.processed`, or admin verification of a processed Paystack refund ID, reconciles receipts. Partial refunds remain pending; REFUNDED requires the full amount. Duplicate receipts do not add twice. A late successful charge on a cancelled/failed order enters refund review instead of fulfillment.
- Unpaid cancellation requires verified failed/abandoned provider status. Unknown/pending payments cannot be cancelled as though unpaid. Open uncertain orders have a scoped support request path.
- DNS/nameserver/transfer/support requests are manual, logged tasks with customer-visible progress. Nameservers change in the asset only after admin confirms the supplier change. Transfer pricing is informational/quoted; automated EPP transfer/transfer checkout is not implemented. Registrant data updates/transfer eligibility require support.
- Renewals quote the **current** enabled renewal price. Expiry advances only after manual supplier confirmation, using the recorded prior expiry; already expired assets require support for registry eligibility. Reminders queue 30/14/7/1 days before actual expiry in Africa/Lagos, once per asset+expiry+day. No automatic renewal/debit.
- Website connection reuses the organization's existing website/template. It does not demand template reselection or replace another configured domain. Status reflects last verification, not continuous DNS/SSL monitoring.

Domain registration is distinct from the website plan's 14-day guarantee: registration eligibility, failed-order full refunds and registry restrictions are explained before payment. Active registrations may not be reversible. Preserve audit/payment/refund records under the business's retention policy; FK constraints deliberately prevent orphaning paid records by deleting an organization.

## Validation and operational limits

`node tests/domain-orders.test.mjs` exercises real PostgreSQL-compatible migrations/queries with PGlite, mock provider responses and no external purchases: input validation, encryption tampering, pricing snapshots, tenant/role access, dedupe/late payments, retries before acknowledgement, fulfillment dates, renewal, full/partial refund receipts, DNS/hosting gates and reminder retries. The whole Business suite also checks legacy billing regressions.

Live database migration, real email delivery, actual Paystack test/live transactions and supplier registration need deployment configuration and operator testing; local tests never establish those are live. Monitor overdue paid/processing orders, UNKNOWN checkout state, refund queues and notification failures. No production registrant data or payment credentials are in test fixtures.
